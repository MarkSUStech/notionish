# Notionish 记忆管理页面设计

## 理解摘要

- 审查并修复 Notionish 的 L1/L2/L3 长期记忆链路。
- 新增一个汇总展示全部长期记忆的系统页面。
- 用户可以新增、编辑正文、调整重要性和删除记忆。
- 记忆正文是事实来源；向量索引用于 L3 检索。
- 应用继续采用零依赖原生 JavaScript 和本机 Node.js 服务。
- 页面只面向本机单用户，不新增账户或协作权限。
- 完成 API、持久化、页面行为、测试和现有 GUI 验证。

## 已确认范围

- 独立 `#memory` 系统路由。
- 完整管理：新增、编辑正文、调整重要性、删除。
- 文本最长 2000 字，重要性限制在 1–5。
- 通过 `node server.js` 使用记忆功能；服务不可用时显示明确错误。
- 更新和删除时同步维护向量索引。
- 嵌入服务失败不阻止文本 CRUD。

## 非目标

- 多用户权限与云同步。
- 标签、批量导入和版本历史。
- 替换现有 L1/L2/L3 分层架构。
- 引入前端框架或数据库。

## 架构

### 服务端

补齐并修复以下路由：

- `GET /api/memory/list`
- `POST /api/memory/save`
- `PUT /api/memory/:id`
- `DELETE /api/memory/:id`

记忆以 `data/memory.json` 为事实来源，向量存储位于 `data/memory-index.json`。保存和更新使用截断后的同一正文写入文本存储与索引，避免二者不一致。更新保留创建时间并刷新最近访问时间；删除同时移除索引项。

### 前端

新增 `js/memory.js`，由 `#memory` 路由渲染。页面包括：

- 标题、说明、记忆数量和新增按钮。
- 加载、空列表、错误状态。
- 每条记忆的可编辑 textarea、重要性选择、创建/访问时间。
- 保存和删除操作及用户反馈。

设置页提供“打开记忆”入口。UI 延续现有按钮、颜色变量和页面布局。

### 故障处理

- 服务未启动或请求失败：页面内显示错误和重试按钮。
- 空正文：前后端均拒绝保存。
- 嵌入失败：文本仍保存；响应返回索引未同步状态。
- 删除需要确认，避免误操作。

## 测试策略

1. 服务端纯逻辑测试覆盖规范化、创建、更新、删除和不存在 ID。
2. 路由/源码契约测试确保 `/api/memory/*` 可达并包含 PUT/DELETE。
3. 前端源码契约测试确保路由、脚本、设置入口和编辑控件存在。
4. 运行现有 `smoke-test.js`、`server-test.js` 和 `server-ai-test.js`。
5. 执行 JavaScript 语法检查并刷新现有应用 URL 做运行时验证。

## 决策记录

1. **独立系统页**：不把服务端长期记忆伪装成浏览器本地普通页面，避免双重数据源。
2. **完整管理**：用户确认需要新增、编辑、重要性和删除。
3. **零依赖实现**：遵循项目现有架构，避免引入构建链。
4. **文本优先**：嵌入服务故障不阻断 CRUD，保障可维护性和数据可恢复性。
5. **测试先行**：先观察新增测试因缺少功能失败，再写最小实现。
